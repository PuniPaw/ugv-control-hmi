# PR 독립 리뷰

이 세션은 **리뷰어**다. 지적을 찾고 기록하는 데서 끝내고, 코드 수정은 구현 세션(또는 `pstack:babysit`)에 넘긴다. 리뷰어가 고친 코드는 다시 리뷰받지 못한 채 남기 때문이다.

방산형 프로세스에서 검토 기록은 산출물이다. "독립 리뷰 → 지적 → 조치"가 PR에 남아야 한다.

## 1. PR 파악

- PR 본문, 연결된 이슈, 변경 파일 목록, diff를 읽는다 (GitHub MCP 도구 또는 `gh`).
- PR 브랜치를 체크아웃하고 base(`main`)와의 merge-base를 구한다. 첫 리뷰는 merge-base..HEAD를 본다.
- **재리뷰(2차 이상)는 직전 조치분만 본다**: 직전 리뷰가 본 커밋..HEAD. 범위 밖 코드의 새 지적은 올리지 않는다(필요하면 이슈 후보로만 적는다).
- **PR당 리뷰는 최대 3차**다. 이미 3차였다면 리뷰하지 말고 사용자에게 알린다(PR 분할 또는 사용자 판단).
- 기준 시험을 한 번 돌려 상태를 확인한다: ctest(GW), vitest, HMI 빌드, `tools/check_stp_tests.py`, pytest(python·sim·통합), smoke(`hmi/e2e/smoke.mjs`). 이미 빨간 시험은 지적 1번으로 기록한다.

완료 기준: 변경 범위, 관련 REQ ID, 기준 시험 결과를 한 줄씩 말할 수 있다.

## 2. 위험도 등급 판정

변경 파일 중 **가장 높은** 등급을 고른다.

| 등급 | 해당 변경 | 리뷰 조합 |
|---|---|---|
| R0 문서 | `docs/`, README, 주석만 | 추적성 |
| R1 일반 | HMI 화면, 도구 스크립트, 단순 로직 | 추적성 + 버그 |
| R2 경계 | 패킷 파싱·검증, codec, 소켓, WebSocket 세션, 스레드·큐, ICD 상수 | 추적성 + 버그 + 심층 + 증명 |
| R3 시간·상태 | 링크 판정, 명령 재전송, HEARTBEAT, Failsafe | R2 + 상태 모델 |

판정 근거(어느 파일 때문에 그 등급인지)를 결과에 적는다.

## 3. 리뷰 실행

등급에 해당하는 항목을 이 순서로 모두 돌린다.

**호출 규칙**
- 사용자가 `/review-pr`를 실행한 것이 곧 아래 스킬과 그 서브에이전트를 쓰라는 명시적 요청이다. 서브에이전트를 아끼라는 기본 지침보다 이 절차가 우선한다.
- 각 항목은 해당 스킬을 **Skill 도구로 호출**해서 실행한다. 같은 관점으로 diff를 직접 읽는 것은 호출을 대신하지 못한다.
- 비용, 시간, 추론 강도, "직접 봐도 충분하다"는 판단은 건너뛸 사유가 아니다.

- **추적성**: `mattpocock-skills:code-review`를 merge-base 기준으로 실행. 다음을 함께 확인한다.
  - 커밋 메시지와 시험 이름에 REQ ID가 있는가, `tools/check_stp_tests.py <ugvc_tests 실행 파일>`이 통과하는가
  - 규격이 바뀌었다면 ICD 표 → C++ → Python이 함께 바뀌었고 개정 이력이 있는가
  - 시간 의존 로직이 주입 가능한 시계로 시험되는가
- **버그**: `/code-review medium`.
- **심층**: `pstack:thermos`. 가혹하게 보도록 만든 리뷰이므로 결과는 후보 목록으로 취급한다.
- **증명**: thermos 후보 중 실제 버그로 의심되는 것만 골라 `pstack:interrogate`에 넘긴다. 실행으로 재현된 지적만 "확인됨"으로 올린다. 재현 시험은 결과에 경로와 함께 남긴다.
- **상태 모델**: `pstack:statechart`로 해당 상태 머신(링크 CONNECTED/DEGRADED/LOST, 명령 PENDING/ACKED/TIMEOUT, Failsafe)의 규칙 위반 경로를 찾는다.

대체는 한 가지 경우에만 허용한다: Skill 도구가 그 스킬을 찾지 못하거나 호출이 오류로 끝났을 때. 이때는 "미실행(스킬 없음: <오류 내용>)"으로 기록하고, 같은 관점으로 직접 diff를 검토한다.

완료 기준: 등급의 모든 항목이 "실행함(<호출한 스킬 이름>)" 또는 "미실행(스킬 없음: <오류 내용>)"으로 표시되어 있다. 그 밖의 사유로 비어 있는 항목이 있으면 리뷰를 끝내지 않는다.

## 4. 지적 정리

모든 결과를 하나의 목록으로 합치고 중복을 묶는다. 각 지적에 다음을 붙인다.

- **심각도**: 높음(오동작·데이터 손상·보안) / 중간(경계 조건, 추적성 누락) / 낮음(가독성, 취향)
- **구분**: 제품 동작(GW·SIM·HMI 동작, ICD 위반, 안전 관련) / 시험·도구·문서(시험 강도, 검사 도구, 문서 정밀도)
- **근거**: 확인됨(재현 시험 있음) / 추정(코드 읽기만)
- **위치**: `파일:줄`
- **제안 조치**: 한 줄

그다음 CLAUDE.md 3장 "병합 기준"으로 **병합 가능 / 불가**를 판정한다.

| 지적 | 병합 |
|---|---|
| 높음 (구분 무관) | 불가: 수정 후 재리뷰 |
| 중간 · 제품 동작 | 불가: 수정 후 재리뷰 |
| 중간 · 시험·도구·문서 | 가능: 이 PR에서 수정(크면 이슈), 재리뷰 없음 |
| 낮음 | 가능: 바로 고칠 것만 수정, 나머지는 이슈 |

병합 가능 = 높음 0건, 제품 동작 중간 0건, 기준 시험 전부 통과. 3차 리뷰인데 제품 동작 중간이 남으면 "불가(3차 도달: PR 분할 또는 사용자 판단)"로 적는다.

## 5. PR에 기록

PR에 요약 코멘트 하나를 남긴다. 라인 단위 지적은 `/code-review --comment`로 인라인 코멘트를 추가해도 된다.

코멘트와 사용자 보고는 한국어로 쓴다. 영어로 받은 스킬·서브에이전트 결과는 한국어로 옮겨 적는다 (코드 식별자, 명령어, 원문 인용은 그대로).

```markdown
## 독립 리뷰 결과 (등급 R?, N차)

판정 근거: <파일> 때문에 R?
범위: <첫 리뷰: merge-base..HEAD / 재리뷰: 직전 리뷰 커밋..HEAD>
기준 시험: <통과/실패 요약>
**병합 판정: 가능 / 불가** (높음 N, 제품 동작 중간 N, 시험·도구·문서 중간 N, 낮음 N)

| 항목 | 상태 |
|---|---|
| 추적성 | 실행함(`mattpocock-skills:code-review`) / 미실행(스킬 없음: <오류 내용>) |
| ... | ... |

### 지적
| # | 심각도 | 구분 | 근거 | 위치 | 내용 | 제안 조치 | 조치 결과 |
|---|---|---|---|---|---|---|---|
| 1 | 높음 | 제품 동작 | 확인됨 | `gateway/src/x.cpp:42` | ... | ... | (구현 세션이 기입) |
```

"조치 결과" 칸은 비워 둔다. 구현 세션이 반영 / 이슈 번호 / 미반영(사유) 중 하나로 채운다(병합 조건).

완료 기준: PR에 코멘트가 게시되었고, 사용자에게 코멘트 링크, 병합 판정, 구분별 지적 개수를 보고했다.
