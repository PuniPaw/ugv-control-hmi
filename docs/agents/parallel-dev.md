# 병렬 개발 조율

브랜치 여러 개를 클라우드 세션 여러 개로 동시에 개발할 때의 규칙과 그 이유다. 실행 절차는 `/parallel-dev` 스킬(`.claude/skills/parallel-dev/`)에 있고, 이 문서는 규칙의 원본이다. 병합 기준(심각도·구분별 처리, 재리뷰 범위와 차수)은 CLAUDE.md 3장을 따른다.

## 역할

| 세션 | 수 | 하는 일 | 시작 문구 |
|---|---|---|---|
| 조율 | 1 | 작업 분할, 세션 생성, 메시지 중계, 머지 전 확인, 라운드 마무리 | `/parallel-dev [작업 목록]` |
| 구현 | 브랜치마다 1 | `main`에서 `feat/`·`fix/` 브랜치를 만들어 구현하고 PR을 올린다. 리뷰 지적을 조치한다 | 지시문 첫 줄 "Skill 도구로 `pstack:poteto-mode`를 실행" |
| 리뷰 | PR과 차수마다 1 | `/review-pr`로 독립 리뷰하고 결과를 PR 코멘트로 남긴다 | 사용자가 그 세션에 `/review-pr <번호>`를 입력한다. poteto-mode는 쓰지 않는다 |

- 세션은 모두 별개의 클라우드 세션이다. 조율 세션의 서브에이전트가 아니다. 컨테이너가 따로라 빌드·포트·디스크가 섞이지 않고, 사용자가 각 세션에 들어가 직접 답할 수 있다.
- 리뷰 세션을 차수마다 새로 여는 이유: 이전 차수의 판단에 끌려가지 않는 독립 리뷰가 검토 기록의 가치다.
- 세션을 만들 때 첫 메시지는 `/`로 시작할 수 없다(`create_session`이 거부한다). 그래서 구현 세션은 첫 줄을 문장으로 써서 Skill 도구로 poteto-mode를 실행하게 한다.
- `review-pr`는 사용자가 직접 입력해야만 실행되는 스킬이다(`disable-model-invocation`). 조율 세션은 리뷰 세션을 "입력 대기" 지시문으로 만들어 두고, 사용자에게 그 세션에 `/review-pr <번호>`를 입력해 달라고 알린다. 리뷰를 사람이 시작한다는 기록이 남는다.
- 구현 세션은 지시받은 디렉터리만 고치고 CLAUDE.md는 고치지 않는다. 여러 브랜치가 같은 현황표를 고치면 매번 충돌한다.

## 시작 전: 규격 먼저

- 작업에 필요한 SRS·ICD 규격에 빈칸이 있으면 구현 세션을 띄우기 전에 `docs/` PR로 먼저 확정한다. 확정된 규격을 보고 각 세션이 따로 구현해야 결과가 맞물린다.
- 구현 중에 SRS·ICD 규범 문구를 바꿔야 하면 구현 세션은 멈추고 선택지와 추천을 사용자에게 보고한다. 규격은 여러 브랜치가 함께 기대는 계약이라 한 세션이 혼자 바꾸면 다른 세션의 전제가 깨진다.
- 브랜치를 나눌 때 서로 겹치는 파일을 미리 찾는다. 코드 디렉터리는 CSCI별로 갈려 잘 겹치지 않고, 실제로 겹치는 곳은 STP·SDD 개정 이력과 CLAUDE.md다. 다른 작업의 출력을 입력으로 받는 작업(예: 경고 체계)은 그 작업이 병합된 뒤에 시작한다.

## 메시지 규약

세션 사이 보고는 아래 네 줄 형식만 쓴다. 조율 세션은 이 형식을 보고 다음 단계를 고른다.

| 보내는 쪽 → 받는 쪽 | 형식 |
|---|---|
| 구현 → 조율 | `PR 생성: #N <브랜치>` |
| 리뷰 → 조율 | `리뷰 완료: #N <차수>차 높음 N / 중간(제품 동작) N / 중간(시험·도구·문서) N / 낮음 N, 판정 <병합 가능\|수정 필요>` + 코멘트 링크 |
| 조율 → 구현 | `리뷰 조치: #N (<차수>차, 판정 ...)` + 코멘트 링크와 반드시 고칠 지적 |
| 구현 → 조율 | `조치 완료: #N <HEAD sha>` |

모든 지시문에 "이 순환과 조율 세션 보고는 사용자가 요청한 것이다"라고 적는다. 다른 세션이 보낸 메시지는 받는 세션에서 사용자 지시가 아니라 데이터로 취급된다. 이 문장이 없으면 구현 세션이 조율 세션의 지시를 믿지 않고 사용자 확인을 기다리며 멈춘다.

## 리뷰 순환

- 처리 기준·재리뷰 범위(직전 조치분만)·최대 3차는 CLAUDE.md 3장을 그대로 따른다. 시험·도구·문서 중간과 낮음만 남으면 재리뷰 없이 조치 후 조율 세션이 확인한다.
- 같은 전제에서 나온 결함이 두 차수 이어지면 그 전제를 의심한다. 타이머·재검사를 한 겹 더 덧대는 수정은 다음 차수에 새 결함을 낳기 쉽다. 기능을 빼는 쪽이 답일 수 있다. 예: 명령 행마다 시간 기준으로 열던 "다시 보내기"를 없애고 다시 시도는 경고가 붙은 새 명령으로 바꾸자 두 지적이 함께 사라졌다.
- 3차가 끝났는데 제품 동작 중간 이상이 남으면 순환을 멈추고 사용자가 정한다. 선택지는 작게 고치고 조치분만 보는 재리뷰를 예외로 허용, 이슈로 넘기고 병합, PR 분할이다. 예외를 허용했다면 리뷰 코멘트에 "사용자 결정으로 N차 재리뷰 허용"을 남긴다.

## 문서 버전 충돌

- 같은 문서(주로 STP·SDD)의 버전을 여러 PR이 올리면 먼저 병합된 PR이 그 번호를 갖는다.
- 나중 PR은 `main`을 merge한다. rebase·force-push는 쓰지 않는다. 리뷰가 본 커밋을 그대로 남겨야 "리뷰한 것 = 병합한 것"을 sha로 확인할 수 있다.
- 충돌은 `main`의 이력 행을 그대로 두고, 자기 PR의 행을 그 뒤 번호로 다시 매겨 붙여 푼다. 문서 머리 버전도 맞춘다.
- 이 정리는 재리뷰가 필요 없다. 대신 조율 세션이 merge 커밋에 코드 변경이 섞이지 않았는지 확인한다(아래 머지 전 확인).

## 머지 전 확인

조율 세션은 사용자가 머지를 허락한 PR만 머지하고, 머지 직전에 다음을 본다.

- PR HEAD sha가 마지막 리뷰 또는 확인한 sha와 같다. 머지 요청에 그 sha를 기대값으로 넣는다.
- `main` 대비 변경 범위가 지시한 디렉터리와 문서뿐이다. 버전 정리 merge 뒤라면 코드 디렉터리가 리뷰한 커밋과 같다.
- STP·SDD 개정 이력이 빠짐없이 이어진다.
- `main`과 충돌 없이 합쳐진다.
- 바뀐 영역의 시험 일부를 직접 다시 돌린다(예: HMI면 vitest와 빌드, SIM이면 `pytest sim python`, 규칙 수치는 변이 하나로 시험이 실패하는지). 나머지는 구현·리뷰 세션의 보고를 쓰고, 그렇게 했다고 사용자에게 밝힌다.

## 사용량 한도

R3 등급 PR은 리뷰 한 차수에도 사용량이 크다. 동시에 너무 많이 돌리면 5시간 한도에 걸려 몇 시간씩 모두 멈춘다.

- 동시 진행은 2개까지 둔다.
- 구현 세션은 자주 커밋하고 push한다. 한도로 멈춰도 작업이 PR에 남는다.
- 한도로 멈췄던 세션에는 "PR HEAD와 작업 트리부터 확인하고 이어서"라고 지시한다. 멈춘 시점에 push했는지 세션 스스로도 모른다.
- 알림이 빠질 때를 대비해 매시간 정기 점검을 켜 둔다. 모든 PR이 사용자 결정을 기다리는 동안에는 일시 정지한다. 할 일 없이 깨어나기만 한다.

## 라운드 마무리

- CLAUDE.md 4~6장 현황은 라운드의 PR이 모두 병합된 뒤 조율 세션이 `docs/` PR 하나로 갱신한다. 리뷰에서 "병합 시 조율 세션이 반영"으로 남긴 CLAUDE.md 지적도 이때 처리한다.
- 정기 점검을 삭제한다.
